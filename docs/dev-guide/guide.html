1. What locus does

  • It compares two versions of OpenAPI documents (3.0, 3.1, 3.2).
  • It prints each changed endpoint in full, like API documentation.
  • It marks each change: green added, orange compatible, red breaking.
  • It exits with 1 on a breaking change, 2 on bad input, else 0.
locus diff "specs/*.yml"                          # base: origin/main (git)
locus diff --source ../old/specs specs            # base: local files

2. The pipeline

Each stage has one job. Each stage returns plain data to the next.

StageFolderJob
Sourcessrc/sources/Patterns to file lists. Git mode copies the base files to a temporary folder.
Loadsrc/load/Parse YAML and JSON. Resolve $refs on demand.
Modelsrc/model/One view tree per endpoint, plus a table of schema definitions.
Diffsrc/diff/Match nodes, compare facts, classify each change.
Rendersrc/render/Print the diff report.
  • The diff runs on the same tree that the renderer prints.
  • So every change the diff finds is visible, and every visible fact is compared.

3. One run, step by step

  • main() builds a new commander program on each call. It never calls process.exit. It returns the exit code.
  • expandPatterns() turns files, folders, and globs into SpecFiles. Each has an id, the key that pairs base and head files.
  • compareFiles() loads each side with its own DocumentStore. It skips files without an openapi field (shared schema files).
  • pairById() pairs documents. Two files named directly pair even with different names.
  • diffDocument() compares one pair. buildReport() counts the endpoints.
  • Input problems throw InputError. main() prints it and returns 2.

4. Git mode

  • The head is the working tree, so uncommitted edits show.
  • The base is the same patterns at the ref (default origin/main).
  • checkoutRef() copies the matched files, then every file their $refs reach, into a temporary folder (tmp-promise).
  • Each round reads all its files with one git cat-file --batch process.
  • The copy mirrors the repository. So relative $refs work the same as in the working tree.
  • Both sides pair by path relative to the current folder (keyByPath()).
  • A plain path that does not exist at the ref is a new file.
  • After this, git mode runs the same code as --source.

5. Loading files and $refs

DocumentStore in src/load/documents.ts owns all file access.

  • load(path) reads and parses one file. JSON uses JSON.parse. YAML allows merge keys (<<) and duplicate keys.
  • loadWithRefs(path) also loads every file that the $refs reach. A file that fails to load becomes a warning, not an error.
  • A Located (src/load/located.ts) is a value with its place: the file and the JSON pointer. document(path) gives a whole file as a Located.
  • loc.at('paths', '/pets') steps to a child. entries() and items() list the members of an object or an array. Only own properties count, so untrusted keys are safe.
  • The pointer text is built on first use. A node gets it as its source.
  • resolve(loc) follows a $ref when asked. It resolves against the file that holds the reference, follows chains, and caches each target. It returns the target as a Located, or the reference that did not resolve.
  • Nothing is dereferenced up front. The parsed files keep their $refs.
  • lineOf(file, pointer) gives the line of a JSON pointer, for a UI that jumps to the spec.
  • Not supported: remote $refs (https://) and $anchors. They become warnings.

6. The model

buildDocument() turns one OpenAPI document into a DocumentModel: an info node, one view tree per operation and webhook, and a table of schema definitions.

View nodes

  • kind: what the node is (operation, parameter, property, response, and so on).
  • key: identifies the node among its siblings. The diff matches by kind and key.
  • label: the display name.
  • direction: request or response (see section 7).
  • attrs: typed facts, such as type, required, maximum. See Attrs in src/model/tree.ts.
  • ref: the id of a schema definition that the node shows.
  • source: the file and JSON pointer where the node is defined.
  • Sections and groups are structural: they have no facts of their own.

References stay references

  • A schema that is only a $ref becomes a node with a ref.
  • The definition is built once per schema and direction, and stored in DocumentModel.schemas.
  • A reference cycle points back to its definition. No special case is needed.
  • "Only a $ref" includes a description next to it, a one-member allOf around it, and a nullable form (oneOf: [X, {type: null}], 3.0 nullable). 3.1 has no nullable keyword, so 3.1 ignores it.
  • A description next to a $ref hides the description of the definition. The renderer then does not show a change of the hidden description.
  • Any other schema is built in place: its allOf members merge into one set of facts.

Keys and normalization

  • Parameters: grouped by location. Header names ignore case.
  • Path parameters: keyed by their position in the path. A rename is not a removal.
  • oneOf/anyOf members: keyed by schema name, then type, then position.
  • Responses: keyed by status code, sorted by code.
  • style and explode hold effective values. An explicit default equals an omitted one.
  • readOnly properties leave request trees. writeOnly properties leave response trees.
  • The 3.0 shim (src/oas/shim30.ts) converts 3.0 schemas to 3.1 form. All 3.0 knowledge stays there.
  • The openapi version is not a fact. A 3.0 to 3.1 upgrade alone shows no change.

7. Direction

Most rules depend on who writes a value.

  • A value the client sends can accept more over time, but not less.
  • A value the client receives can promise more over time, but not less.
  • Example: a new enum value is compatible in a request, but breaking in a response.
  • Webhooks and callbacks flip both directions.

8. The diff

src/diff/diff.ts compares two models and builds the report.

Matching

  • Operations: by operationId (when unique), then method and path, then method and path with parameter names ignored.
  • Other nodes: by kind and key.
  • Variants: when names change (a renamed component), removed and added variants pair by position.
  • Order: head order. A removed node shows where it was. Removals print before additions.

Comparing

  • Node on both sides: compare its own facts. Each changed fact gets a verdict from the rules.
  • Node on one side only: the rules classify it once. Its whole subtree inherits that severity.
  • References on both sides: the two definitions are compared once. Every use shares the result.
  • A reference on one side only: it is expanded one level and compared in place.
  • Inside not: every change is breaking, because not reverses the direction rules.

Status, verdict, impact

  • status: added, removed, changed (own facts changed), or unchanged.
  • verdict: severity (breaking or compatible) and a reason.
  • impact: the worst change in the subtree. It rolls up to the endpoint and the document.
  • A subtree includes the definitions that its references point to.
  • The diff itself sets no impact. In a reference cycle, a definition diff is still in progress when the cycle reaches it. So settleImpacts() sets every impact after the diff. It repeats the definitions until no impact changes.
  • Exit code 1 means some document has impact "breaking".

9. The rules

  • src/diff/rules.ts holds every rule. docs/breaking-changes.md describes the same rules in prose. Keep the two in step.
  • classifyAdded() and classifyRemoved(): a node on one side only.
  • classifyAttr(): one changed fact.
  • Helpers express the direction logic: directional(), constraint() (tightened or loosened).
  • A reason says what changed and, when it matters, the direction: "maximum decreased (client sends)".

10. The report

DiffReport in src/diff/report.ts is the output structure for every renderer. It holds no colors or markup.

  • Each document has its own schemas table of definition diffs.
  • A node's ref points into that table. Renderers look it up while they print.
  • endpointOutcome() gives what happened to an endpoint as a whole.

11. Rendering

  • show(node, definitions) in format.ts merges a node with its definition: facts, changes, and children.
  • Markers: + added, - removed, ~ changed. Colors repeat the markers.
  • A breaking change carries [breaking: reason], so the output works without color.
  • A cycle prints (recursive).
  • After 400 lines in one endpoint, the endpoint shows only the shortest paths to its changes:
    • changeDistances() gives each definition the number of references to its nearest change.
    • A reference expands only when its definition is closer to a change than the enclosing definition.
    • A definition that already printed shows (shown above).
    • Unchanged nodes print as one count line: … 12 unchanged, not shown.
  • Why shortest paths: in a spec like Stripe, almost every schema reaches every other schema. So almost every schema has a change inside, and "expand what changed" prints almost everything.
  • format.ts holds the text helpers (type labels, badges, change lines). An HTML renderer can reuse them.

12. Tests

  • Unit tests sit next to the code: src/**/*.test.ts.
  • src/testing/build-yaml.ts builds a model from inline YAML.
  • End-to-end tests call main() in-process and snapshot the whole run: exit code, stdout, stderr.
  • The corpus: test-e2e/corpus/<area>/<scenario>/ holds base/, head/, scenario.yml (expected class), and output.txt (snapshot).
  • The git test builds a temporary repository with an empty global git configuration.
npm run check                                   # typecheck, lint, tests, build
npx vitest run src/diff/rules.test.ts           # one file
npx vitest run test-e2e/corpus.test.ts -u       # update snapshots, then read the diff

13. Recipes

Add a new fact

  1. Add the attribute to Attrs in src/model/tree.ts.
  2. Set it in the model: schemaAttrs() for schemas, build.ts for other nodes.
  3. Classify its changes in classifyAttr() in rules.ts.
  4. Add a row to docs/breaking-changes.md.
  5. Show it: a badge or detail in format.ts.
  6. Test: a rule row in rules.test.ts, and a corpus scenario.

Debug a wrong verdict

  1. Make a corpus scenario that shows the problem.
  2. Find the reason text in the output. Search for it in rules.ts.
  3. Check the node's direction and kind. Most wrong verdicts come from one of these.

Add a renderer

  1. Take a DiffReport from compareFiles().
  2. Walk documents, then operations. Use show() for each schema node.
  3. Keep a set of open definition ids, to stop at cycles.
  4. Reuse typeLabel(), badges(), details(), and describeChange().

14. Glossary

View treeThe model of one endpoint: nodes with facts.
DefinitionA schema that $refs point to, built once per direction.

ImpactThe worst change in a subtree.
